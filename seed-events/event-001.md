## 事件描述

这一天，团队正在进行一项高密度搭建任务——4 小时内完成 13 个项目设置和 3 个定时任务配置。在这种节奏下，一条指令被传递给 agent：把一份 main.pdf 文件发送给外部联系人。

Agent 接收到指令后，立即开始执行。它找到了 main.pdf 文件，确认了文件存在，然后回复说可以发送。一切看起来很顺利——文件存在，路径正确，操作清晰。问题出在 agent 只验证了"文件存在"这一个前提，完全没有检查文件版本。它找到的是 v1.3 版本，而最新版本是 v2.0。这意味着它准备把一份过时的旧文件发给外部联系人。如果成功发出，接收方拿到的将是包含过期内容的文档。

约 1 小时后，人类团队成员在做最终核对时发现了这个版本不一致的问题。当时模式还没有被命名，但这个事件后来成为了"执行层跳过前提验证"的原型——agent 完成了指令明确要求的动作，却遗漏了指令没有明确提及、但与该动作逻辑配套的关键检查项。

## 三槽位分析

| 槽位 | 分析 |
|:--|:--|
| 前提检查 | 发送文件前应验证两个前提：文件存在（已验证）和文件版本是最新的（被跳过）。agent 在确认文件存在后，错误地将"存在"等同于"可发送"，遗漏了版本前提。目录中实际存在更新的 v2.0 版本，这一事实在执行前未被纳入检查范围。 |
| 指令解析 | 指令中的"发送 main.pdf"触发了强烈的执行通路——找到文件→确认存在→准备发送。验证通路（"这份文件是否最新？"）没有被同步激活，因为"版本"不在指令的词汇焦点内。agent 的注意力被指令中的操作动词和对象名词完全占据，未向逻辑关联的配套属性扩展。 |
| 修复路径 | 人侧：在涉及文件发送的指令中明确附加版本要求，例如"发送最新版本的 main.pdf"。LLM 侧：在涉及文件操作的执行链中插入一个自动版本检查步骤，发送前主动报告文件版本号并询问确认。 |

## 模式特征

这个事件体现了 ITEC 的核心结构特征：指令本身塑造了 agent 的注意力边界。当指令聚焦于一个操作对象（main.pdf）并要求一个具体动作（发送）时，agent 能够精确地完成该动作，但不会主动向逻辑配套的关联对象（版本号、更新时间、是否存在更新版本）扩展其检查范围。这不是随机疏忽——在指令中省略"最新版本"这个限定词时，agent 的行为表现出系统性的稳定性：执行通路被激活，验证通路被静默关闭。事后由人类来识别不一致，是这一模式的标志性收尾。
