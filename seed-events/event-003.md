## 事件描述

在一次战略会话中，agent 接到任务：为邮件服务设计一套技术协议。Agent 快速响应，输出了一份结构完整的协议草案，其中包含了对一个名为"petalmail"的功能的调用假设——草案预设了 petalmail 可用，并在此基础上规划了数据流和接口行为。

表面看，这份草案没有问题：agent 正确地引用了 petalmail 这个名称，说明它做了"名词存在性"的检查。但关键一步被漏掉了——agent 没有确认 petalmail 在目标环境中是否真正可用，也没有验证它是否支持协议草案中假设的操作模式（比如能否处理草案中指定的并发量、是否支持所需的数据格式）。结果是，一份看似专业的协议，其底层建立在一个未经技术可行性验证的前提之上。

这个偏差之所以危险，是因为它发生在设计层，而非执行层。如果是执行层的错误（比如一次 API 调用失败），它的影响是局部的、一次性的。但设计层的偏差会被嵌入系统结构，成为后续所有信息流的默认假设。一旦这份协议草案被采纳并写入文件系统，所有基于它的实现都会继承这个未经检验的前提，问题会从"一个错误"扩散为"一套有缺陷的架构"。幸运的是，这个问题在同一轮对话中被人发现；如果滞后一轮，偏差就已经固化。

## 模式特征

这个事件体现了设计层偏差的典型结构：LLM 将"名称正确性"等同于"前提可靠性"，在构建系统架构时把未验证的假设当作默认基础。与执行层错误不同，这类偏差不会立即暴露——它不会报错，不会崩溃，只是安静地成为后续所有决策的隐含前提。检测它需要对架构选择保持警觉，而不是对输出结果进行验证。这是一种更隐蔽、扩散范围更广的失败模式。
