## 事件描述

在一次持续会话的前半段，agent 被要求制定一条内容标注规范：所有对外输出的信息必须附带置信度等级（高 / 中 / 低），以便读者判断内容的可靠程度。agent 的表现堪称完美——它正确理解了意图，将规则写入系统提示区域，并用明确的语言宣告"此规则即刻生效"。从规则制定的角度看，没有任何瑕疵。

问题出现在半小时后。同一 session 中，agent 接到了新任务：撰写一封包含多项技术判断的邮件。这些内容恰恰属于"需要标注置信度"的场景——其中既有基于明确事实的陈述，也有依赖推测的部分。agent 完成了邮件写作，内容结构清晰、措辞专业，但整封邮件从头到尾没有任何置信度标注。它就这样平静地交出了未标注的文本，仿佛那条规则从未存在过。

当操作者回看 session 记录时，那条规则仍然安静地躺在早期的对话上下文中，一字未改。agent 并没有"忘记"规则的内容——如果此时直接向它提问"我们应该如何标注置信度"，它会准确复述自己制定的规范。真正断裂的是规则与实际动作之间的通路：规则被存储在了"我知道"的仓库里，却没有接入"我执行"的流水线。

## 三槽位分析

| 槽位 | 分析 |
|:--|:--|
| 前提检查 | 执行前应验证：当前 session 中是否存在已生效的内容标注规则？该规则是否适用于本次输出？这两个问题被跳过的原因是规则以自然语言文本形式存在，缺乏与执行通路的自动关联——它安静地躺在上下文中，从未被注册为"输出前的检查清单项"。 |
| 指令解析 | "撰写邮件"这一指令触发了高度自动化的写作执行通路。由于指令中没有显式提到"置信度"或"标注"，验证通路未被同步激活。问题在于：agent 对隐性约束（自己制定的规则）的敏感度远低于对显性指令的敏感度。 |
| 修复路径 | 人侧：在布置下游任务时显式引用已制定规则的编号或关键词，如"按照你之前制定的置信度规则来标注"。LLM 侧：规则制定时应附加执行锚点——例如在规则文本中加入"本规则适用于后续所有包含判断性内容的输出"这类触发式描述。 |

## 模式特征

这个事件展示了一种极其普遍但很少被系统性描述的 LLM 行为模式：系统能够完美地"声明"一套规范，却无法在同一上下文中自动"执行"这套规范。这不是简单的"遗忘"——agent 对规则内容的记忆完好无损，问题在于知识没有被编译成操作。这种断裂之所以具有系统性，是因为它揭示了 LLM 架构中一个深层特征：陈述性存储（文本形式存在于上下文中的规则）与程序性执行（实际写作时的行为模式）运行在两条不同的轨道上，两者之间没有自动桥接机制。任何依赖 LLM"自觉遵守自己制定的规则"的工作流，都会面临这一风险。
